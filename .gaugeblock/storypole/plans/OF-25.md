# Task Plan: GB-123 — Implement Topological DAG Parallel Execution (jobs = num_cpus) in outfeed

## 1. Problem Statement
`outfeed release --all` accepts `-j / --jobs`, but `execute_suite_plan()` in `suite_exec.rs` executes a strictly serial loop over `plan.entries`. Member tools that do not depend on each other's unreleased changes are compiled and verified sequentially, causing massive wall-clock latency.

---

## 2. Technical Blueprint
1. In `outfeed-cli/src/args/release.rs`:
   * Set default `jobs = num_cpus::get()` or `std::thread::available_parallelism().map(|n| n.get()).unwrap_or(4)`.
2. In `outfeed-core/src/suite_exec.rs`:
   * Partition `plan.entries` into topological dependency waves:
     * Wave 1: `miter`
     * Wave 2: `storypole`, `sawhorse`, `dado`, `rabbet` (concurrent)
     * Wave 3: `chalkline`, `batten` (concurrent)
     * Wave 4: `joiner`
     * Wave 5: `benchwork`, `outfeed` (concurrent)
   * Execute each wave using `tokio::task::JoinSet` with a bounded semaphore sized to `opts.jobs`.
3. In `progress.rs`:
   * Ensure `ProgressReporter` implementations safely handle multi-threaded progress updates with atomic stdout synchronization.

## 4. Implementation Notes (as executed)

* **Scoped threads instead of `tokio::task::JoinSet`.** `Joinset::spawn` requires `'static + Send`
  futures, but `release_entry` borrows `&Path`, `&ReleaseOpts` and `&dyn ProgressReporter`. Satisfying
  it would force `Arc<dyn ProgressReporter>` through the public `release_all`/`execute_suite_plan`
  surface. `std::thread::scope` lends the borrows safely, and true parallelism is required anyway
  because the release work is dominated by **blocking** `std::process` calls (`cargo`, `git`) that a
  single async task can only interleave, never overlap. Each worker therefore drives its own
  current-thread Tokio runtime.
* **Module layout.** `src/suite_waves/mod.rs` (partitioning, entry execution, worker pool) plus
  `src/suite_waves/tests.rs`, keeping both under the 250-line law; `suite_exec.rs` shrank to a
  70-line wave driver.
* **Ordering contract.** Wave *membership* comes from `SUITE_RELEASE_WAVES`; order *within* a wave
  follows plan order, and unmapped repositories trail the schedule instead of being dropped.
* **Disk-guard serialization.** A `Mutex<()>` shared by all workers wraps
  `headroom::enforce_disk_headroom`, so parallel releases can never prune `target/debug/deps`
  beneath an in-flight build (the hazard flagged in `PERF_AUDIT_PLAN.md` §7).
* **Failure containment.** Worker panics are converted to `OutfeedError::Install("… panicked")`
  rather than unwinding the process, and results are returned in entry order regardless of
  completion order.
* **Known limitation (by design).** The suite compiles into one shared `target/` directory, so cargo
  serializes actual compilation on its target-directory lock; the parallelism pays off on git,
  registry, LLM and test-execution work. `--jobs 1` restores strictly serial behaviour.

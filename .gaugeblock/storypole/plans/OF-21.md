# GB-101: Add outfeed publish --all, crates.io registry verification, and release self-healing

## Context & Problem Statement
During release orchestration, `outfeed release` commits manifests and creates git tags in Step 1 of the apply phase. When a subsequent step fails (such as running out of disk space, network interruption, or skipped publication):
- The git tag remains committed locally on `HEAD`.
- On all future runs, `outfeed release` checks `git log <latest_tag>..HEAD`, sees 0 unreleased commits, and marks the repository as `Skip (Clean)`.
- It never queries crates.io to verify if the tagged version actually exists in the registry.
- As a result, `rabbet` remained at `0.0.1-alpha.1` on crates.io despite being tagged `v0.1.0-beta.3` locally, and `outfeed` remained at `0.1.0-beta.1` despite being tagged `v0.1.0-beta.5` locally.
- Furthermore, `outfeed publish` currently only accepts a single repository and lacks an `--all` flag, while `scripts/publish-crates.sh` hardcoded only 7 repositories.

## Invariants & Design Decisions

### 1. Registry Inspection Module (`outfeed-core/src/registry.rs`)
- Query published crate versions from crates.io using `cargo search <crate> --limit 1` or sparse index lookup.
- Provide:
  - `get_published_crate_version(crate_name: &str) -> Result<Option<String>, OutfeedError>`
  - `is_version_published(crate_name: &str, target_version: &str) -> Result<bool, OutfeedError>`
  - `are_repo_crates_published(repo_dir: &Path, target_version: &str) -> Result<bool, OutfeedError>`

### 2. Self-Healing in `plan_suite_releases` & `execute_suite_plan`
- In `plan_suite_releases`, when a repository has 0 new commits since its latest tag, inspect if its member crates at that version are published on crates.io.
- If any member crate is not published on crates.io:
  - Set `action: SuitePlanAction::PublishPending`.
  - Format table displays `Publish (Pending)`.
- In `execute_suite_plan`:
  - When encountering `SuitePlanAction::PublishPending`, automatically invoke `publish_repo` to self-heal and publish the pending release.

### 3. Suite-Wide Publishing (`publish_all` & `outfeed publish --all`)
- Implement `publish_all` and `publish_all_with_progress` in `outfeed-core/src/publish.rs` to publish all suite member crates in topological order.
- Add `pub all: bool` to `PublishArgs` in `outfeed-cli`.
- Update `scripts/publish-crates.sh` to delegate to `outfeed publish --all "$@"`.

### 4. Visibility in `outfeed status`
- In `outfeed status`, if a repository has 0 unreleased commits but its version is unpublished on crates.io, display `⚠️  unpublished (crates.io: <ver>)` instead of `✅ clean`.

### 5. File Size Constraints (Law 1)
- Ensure all created and modified files remain strictly below 250 LOC.

## Execution Plan & Verification Steps
1. Create `outfeed-core/src/registry.rs` with version checking and unit tests.
2. Add `SuitePlanAction::PublishPending` to `outfeed-core/src/suite_plan.rs`.
3. Add `publish_all` and `publish_all_with_progress` in `outfeed-core/src/publish.rs`.
4. Update `execute_suite_plan` in `outfeed-core/src/release.rs` to handle `PublishPending`.
5. Update `outfeed-cli/src/args/delivery.rs` and `outfeed-cli/src/commands/publish.rs` for `--all`.
6. Update `outfeed-cli/src/commands/status.rs` to flag unpublished registry status.
7. Update `scripts/publish-crates.sh` to delegate to `outfeed publish`.
8. Verify with `cargo test -p outfeed-core -p outfeed-cli`, `cargo fmt`, `cargo clippy`.
9. Publish `rabbet` and `outfeed` to crates.io and verify live status.

# Task Plan: GB-125 — Port Crates.io 429 Rate-Limit Parser, 30s Terminal Countdown, and Sparse Index Polling

> **Task Key:** `GB-125`  
> **Parent Epic:** `GB-121`  
> **Scope:** `outfeed-core`  
> **Status:** Planned

---

## 1. Problem Statement
When publishing member crates, `outfeed` has zero retry or rate-limit handling. A Crates.io `429 Too Many Requests` response immediately hard-crashes the entire release. Furthermore, `outfeed` sleeps a fixed 15 seconds after every crate published, wasting 5–7.5 minutes across the suite.

---

## 2. Technical Blueprint
1. In `outfeed-core/src/publish.rs`:
   * Implement regex parser for Crates.io 429 responses (matching RFC 2822 dates and integer seconds, ported from `scripts/reserve-namespaces.sh`).
   * When a 429 is received, enter an active cooldown loop with 30s updates through `reporter.on_update()`.
   * Automatically retry publishing up to 3 times upon cooldown expiration.
2. In `publish.rs`:
   * Replace the blind `sleep(15)` with an active HTTP poll against `https://index.crates.io/` every 500ms.
   * Proceed immediately once the new version is returned by the sparse index (typically 2–4s).
3. In `outfeed-core/src/registry.rs`:
   * Replace slow `cargo search` CLI calls with direct HTTP checks (`https://crates.io/api/v1/crates/{name}`).

---

## 3. Execution Steps
* **Step 1:** Implement 429 / `Retry-After` parsing and the countdown retry wrapper (`src/rate_limit.rs`).
* **Step 2:** Implement crates.io sparse-index path/version helpers and 500 ms polling (`src/index_poll.rs`).
* **Step 3:** Wire retry + index polling into `publish.rs` and make the registry check sparse-index-first.
* **Step 4:** Tier 2/3 verification (`cargo nextest run --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`).

---

## 4. Implementation Notes

* **Module split, not `publish.rs` growth.** The parsers live in `rate_limit.rs` and the index logic
  in `index_poll.rs` so `publish.rs` stays well inside the 250-line law and the pure parsing rules
  stay unit-testable without a network.
* **Cooldown semantics.** `Retry-After` accepts integer seconds or an RFC 2822 HTTP-date (parsed with
  `chrono`); when neither is present the resolver falls back to a 30 s default. The retry wrapper
  reports a countdown through `reporter.on_update` and gives up after 3 attempts.
* **Index polling replaces the blind sleep.** `delay_secs` becomes the *timeout budget* for
  `wait_for_index_version`, which polls `https://index.crates.io/<shard>/<name>` every 500 ms and
  returns as soon as the published version appears (typically 2–4 s). A timeout is non-fatal: the
  release proceeds, matching the previous best-effort behaviour.
* **Registry lookup.** `get_published_crate_version` prefers one sparse-index request and falls back
  to the existing `cargo search` parser when the index is unreachable (offline/air-gapped CI).
* **Dependency.** `reqwest` blocking + rustls is added to `outfeed-core`; it is already in the build
  graph through `sawhorse-core`, so no new transitive compilation is introduced.
